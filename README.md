# SoC Platform & Pre-Silicon Validation Lab

> A host-native behavioral virtual SoC platform for firmware, driver
> development, validation and performance analysis before physical hardware
> exists.

## What problem it solves

SoC software (firmware, drivers, board/platform layers) is usually written
against hardware that does not exist yet. This project builds a small,
fully deterministic virtual SoC — CPU, memory map, MMIO peripherals,
interrupt controller, timers, UART, DMA, performance counters — plus the
firmware, RTOS scheduling, Linux-facing driver layer, and automated
validation/benchmark harnesses needed to develop and characterize system
software pre-silicon-style: boot, data movement, interrupts, scheduling,
faults, and recovery, all measured in model ticks.

## Architecture

```text
Application (tasks / stream consumer)
    ↓
RTOS scheduler (FreeRTOS semantics, modeled) / Linux driver API (userspace model)
    ↓
C firmware drivers + HAL (boot, UART, timer, DMA, INTC)
    ↓
Virtual SoC: CPU / Memory / INTC / Timer / UART / DMA / PERF   (soc/, Python)
    ↓
Python validation harness + benchmarks (host controls the experiment)
```

The register map is frozen since Phase 1 (`docs/soc-spec.md`,
`firmware/include/soc_regs.h` generated by `tools/reggen.py` — do not
hand-edit). Time is shared model ticks: every scheduler tick steps the
SoC once, so peripherals advance underneath tasks.

## Why the platform was modeled

Determinism. Every benchmark guarantees identical results across reps
(`deterministic_across_reps: true` everywhere), which makes priority,
burst, buffer, and fault effects attributable to the variable under test
instead of noise. The price — stated in `docs/limitations.md` — is that
no number here is hardware data: MMIO is combinational, waits are modeled
parameters, and there is no contention, caches, silicon, or kernel.

## What firmware/drivers were implemented

* C firmware (host-native via CMake): boot (`.data`/`.bss`, self-check),
  UART/timer/DMA/INTC drivers against the generated register header,
  MMIO shim, smoke-tested app.
* Python RTOS scheduler (`rtos/`): priority-preemptive tasks, queues,
  notifications, mutexes, delays/periodic waits; Acquisition, Processing,
  Telemetry, Diagnostic tasks.
* Userspace Linux-facing driver (`linux/`): app → driver → MMIO → device
  layering, opaque buffer handles, DMA-style transfers, polling/IRQ
  completion, timeouts, arena allocation.

## Validation approach

`validation/` (pytest): boot, bus errors, UART, timer, INTC priority,
DMA correctness/burst, CPU-vs-DMA helpers, fault injection (DMA/UART/
storm/MMIO/reset/recovery-machine), RTOS core+system, Linux platform —
fresh SoC + `boot()` per test, destination byte-compare on every data
path, determinism re-runs, no “must be faster” assumptions.

## Benchmark methodology

One CLI per study, fresh state per cell, provenance
(measured/derived/modeled) on every metric, results + plots gitignored:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cmake -S firmware -B firmware/build && cmake --build firmware/build
python3 -m pytest validation/ -q

python3 benchmarks/boot_time.py --config configs/base.yaml
python3 benchmarks/cpu_vs_dma.py --config configs/base.yaml \
  --sizes 16,64,256,1024,4096,16384 --bursts 1,2,4,8,16 \
  --completion both --reps 5 --out results/cpu_vs_dma_phase4.json
python3 tools/plot_dma.py --inp results/cpu_vs_dma_phase4.json --outdir results/plots

python3 benchmarks/fault_injection.py --config configs/base.yaml \
  --faults dma-invalid,dma-timeout,uart-stuck,irq-storm,mmio-invalid \
  --reps 5 --out results/fault_injection.json
python3 tools/plot_faults.py --input results/fault_injection.json

python3 benchmarks/rtos_scheduling.py --config configs/base.yaml \
  --reps 5 --out results/rtos_scheduling.json
python3 tools/plot_rtos.py --input results/rtos_scheduling.json

python3 benchmarks/linux_platform.py --config configs/base.yaml \
  --sizes 64,256,1024,4096,16384 --reps 5 --out results/linux_platform.json
python3 tools/plot_linux.py --input results/linux_platform.json

python3 benchmarks/final_matrix.py --config configs/base.yaml \
  --sizes 64,1024,4096,16384 --reps 3 --out results/final_matrix.json
python3 tools/final_report.py --input results/final_matrix.json \
  --out results/final_report.md
python3 tools/final_plots.py --input results/final_matrix.json \
  --outdir results/plots
```

## Key measured findings (all within the configured virtual SoC model)

* **Boot:** reset → main in 5 ticks, deterministic.
* **Data movement:** CPU copy 3 ticks/word; DMA `words*1 + (bursts-1)`;
  burst 1→16 cuts 16KB DMA 8191→4351 ticks; sustained 3.2 B/tick under
  DMA pressure (8×16KB back-to-back).
* **Interrupts:** 250/250 storm IRQs handled (50/100 ticks), mixed storms
  drain strictly 1, 2, 0; polling vs IRQ completion take identical ticks
  here — the tradeoff is reads vs IRQs, not speed.
* **RTOS:** priority swap on identical overload halves mean latency
  (107.2 → 57.1) and un-starves telemetry; load knee proc-4→proc-8 vs a
  9-tick deadline; queues trade 19→0 drops for 0%→87.5% misses.
* **Linux path:** depth-1 rings halve throughput; zero mismatches in all
  cells; one genuine model bug found and fixed (post-START SRC corruption
  → ERR_ADDR instead of escaping the tick loop).
* **Faults:** invalid DMA fails synchronously with zero corruption;
  stuck faults caught by tick budgets (DMA 76, UART 20); 5/5 mid-DMA
  resets recovered; 20/20 illegal accesses rejected; 3/3 comm timeouts
  detected with clean abort-to-idle.
* **Bottlenecks (derived shares):** per-word CPU cost vs DMA transfer
  time; burst overhead at small bursts; queue waits under backlog;
  single-channel serialization. Setup/ACK shares read ~0 only because
  MMIO is combinational in this model.

## Limitations

`docs/limitations.md`: model-only ticks, combinational MMIO, modeled
waits/budgets, no contention/caches/masters, single DMA channel, bounded
fault classes, 16KB transfer cap, scheduler models (not ports) FreeRTOS
semantics with no priority inheritance, userspace (not kernel) Linux
layer, no RTL. Nothing here is ARM/MCU/silicon data.

## Reproducibility

Pinned CLI commands above; `requirements.txt` (`pytest`, `pyyaml`,
`matplotlib`); every benchmark asserts `deterministic_across_reps` and
